## Условие (дословно)

"Expense Receipt Assistant"

Task:

1. Trigger (choose one): a Form Trigger (name, email, department, receipt photo) OR a Gmail Trigger that only picks up receipt emails.
2. Basic LLM Chain + Structured Output Parser reads the image → merchant, date, total, currency, category.
3. Not a receipt or no total → ask the employee for a new photo.
4. Data Table check skips duplicates.
5. Import expense_policy.csv as a Data Table; Switch → approve / ask manager / reject.
6. Manager approval: Send and Wait with a Custom Form (decision, amount, comment).
7. Save to an "expenses" Data Table and email the employee the decision.

Bonus:

1. Monday report to finance per department and category (Summarize + Basic LLM Chain).
2. AI Agent chat: "How much did I spend on travel?" using a sub-workflow as a tool.
3. Retry On Fail, an error output for unreadable images and an Error workflow alert.

Materials: "HW6 materials" folder (6 receipts + expense_policy.csv)

## Бележки за подобрение на дизайна (не се имплементират; влизат в Sticky Note)

1. **Давност на разписката:** политиката няма срок (`receipt_03` е от 18.12.2025). Подобрение: колона в политиката с максимална давност в дни и правило в Switch -> ask manager/reject. Не се имплементира (решение на Здравко, 2026-10-16).
2. **Забравена заявка (ред `pending`, който блокира повторно подаване):** сега се трие ръчно. Варианти: (a) Limit Wait Time на Send and Wait + обработка на изтичането (статус `expired`, имейл до служителя и мениджъра); (b) ежедневен чистачен workflow по `submittedAt` - напомняне, после `expired` или изтриване; (c) `pending` по-стар от N часа не се брои за дубликат; (d) ръчно изтриване (текущо). Препоръка: (a) + (b) като предпазна мрежа. Не се имплементира.
3. **По-строг идентификатор на дубликат:** номер на бон, ЕИК, уникален номер на фискалното устройство, QR код; проверка дали AI-генерираните бележки отговарят на българското законодателство.
4. **Атомарно резервиране** при едновременни подавания; сверяване на името на госта със служителя.
5. **Ред `pending` след грешка в изпълнението (добавено 2026-10-17):** ако изпълнението пропадне след `Reserve Expense` (напр. Gmail към мениджъра откаже), редът остава `pending` и блокира повторно подаване, въпреки че Error workflow изпраща Telegram съобщение. Подобрение: стъпка (в основния поток или във втори Error workflow), която намира реда по `submissionId` и го маркира `failed` с коментар, а проверката за дубликат не брои `failed`; така служителят може да подаде отново. Покрива и случая, когато мениджърът не отговаря (виж т. 2). Не се имплементира.
